# Milestone protocol

The machine-readable source of truth is [milestones.json](milestones.json), validated by
[milestones.schema.json](milestones.schema.json). Agents and automation must read it before changing
Agent 365, WorkIQ, Teams identity, or Microsoft Purview integration.

The document declares `protocolVersion: 1` and `currentMilestone: "M7"`. Each milestone entry carries
its `status`, its `scope` and `prohibited` lists, the `allowsTenantReads` and `allowsTenantMutations`
flags, and — where activation is gated — `requiresExplicitUserActivation` and the exact
`activationPhrase`. This README summarizes that file; where the two disagree, the JSON wins.

## Transition rules

1. Work is allowed only when it belongs to the milestone identified by `currentMilestone` and that
   milestone has `status: active`.
2. A planned milestone with `requiresExplicitUserActivation: true` cannot be started by inference,
   package presence, an existing scaffold, or a broad request to continue. The user must provide its
   exact `activationPhrase` in a new instruction.
3. Updating `currentMilestone` and milestone statuses is a separate reviewable change. Do not combine
   it with tenant mutations.
4. Read-only validation may run when `allowsTenantReads` is true, but online checks require explicit
   command switches. Validation tools never log in for the user.
5. Tenant mutations require `allowsTenantMutations: true`, a successful documented dry run where the
   CLI supports it, and explicit user approval after the dry-run output is shown.
6. Package references and host adapter code prove only code readiness. They do not prove Agent 365
   registration, WorkIQ consent, Purview policy enforcement, publication, or instance approval.

## Completed milestone: M0

M0 established foundation and validation automation: the Microsoft Agent Framework application
structure, Agent 365-compatible host boundaries, the standalone MCP services, a thin Teams package,
read-only readiness validation tools, and build/test/local-health automation. It ran with
`allowsTenantReads: true` and `allowsTenantMutations: false`.

M0 explicitly prohibited Agent 365 tenant onboarding; `a365 setup`, `publish`, `cleanup`, and
permission mutations; WorkIQ catalog mutation or `ToolingManifest.json` generation; Microsoft Purview
package installation or middleware wiring; Purview policy creation or modification; and production
deployment. Those capabilities arrived only with M1.

## Completed milestone: M1

M0 and M1 are complete. M1 established the governed Agent 365 onboarding, dual child identities,
OBO runtime, Purview enforcement boundary, and production deployment baseline. It was the first
milestone with `allowsTenantMutations: true`, and it required explicit activation by the exact phrase
`Start milestone M1`.

Its recorded acceptance evidence covers eight conditions: blocked input never reaches the model;
blocked output and streaming content never reach the channel; Purview service failures fail closed;
sensitive tool arguments and results are protected or WorkIQ remains disabled; Agent 365
CLI-generated blueprint and tooling artifacts exist; Entra scope inheritance checks pass;
observability contains no raw prompts, tool data, or credentials; and an approved agent instance
responds through Teams.

The M1 implementation must use fail-closed Purview protection for textual input and output, keep
telemetry sensitive-data capture disabled, and add a separately tested guard for MCP/WorkIQ tool
arguments and results. Agent Framework Purview middleware does not automatically protect tool data,
system instructions, binary content, logs, or telemetry.

CLI-owned artifacts must be generated by the live Agent 365 CLI and never fabricated or hand-edited:

- `a365.generated.config.json`
- historical `ToolingManifest.json` artifacts, if any, generated during M1-era tooling work
- published manifests and packages containing real tenant identifiers

This repository uses one Blueprint for two child identities: the existing AI Teammate identity and
a distinct OBO identity. Frontend-specific CLI state must remain isolated, and no workflow may run
`a365 cleanup blueprint` while either child is active.

M2 preserves its historical production OBO governance and Insider Risk Management checklist. Its

content-activity evidence, Insider Risk Management readiness, and a patch-versioned package build.
Its activation phrase is `Start milestone M2`. Fresh cross-channel, Purview, and deployment alignment
is owned by active M7; do not use M2 history as current deployment or acceptance authority.

The durable execution checklist and sanitized evidence log are in
[M2-obo-governance.md](M2-obo-governance.md). Each deployment, publication, consent, or policy
mutation requires a reviewed dry run and explicit approval.

structured logging. It remains blocked with its checklist preserved while M7 owns current production

## Current milestone: M7

WorkIQ is currently disabled. Do not create `ToolingManifest.json` or run frontend-owned Agent 365
CLI package commands in this backend while M7 is active.

M7 preserves the completed backend-mirror removal and coordinates end-to-end production alignment
for OBO Teams, OBO Direct Line, and AI Teammate. This repository exclusively owns shared runtime,
infrastructure, tests, tools, and deployment. Each frontend exclusively owns its channel/package
workflow. The current host checkpoint is revision `0000028`; Direct Line has isolated pre-model DLP
evidence on that revision, while OBO Teams and AI Teammate still require sanitized same-revision
replays. Every production deployment, package publication, consent change, or governance-policy
mutation requires a reviewed dry run, rollback boundary, and explicit approval.

The execution checklist and sanitized evidence log are in
[M7-end-to-end-alignment.md](M7-end-to-end-alignment.md). The completed frontend/backend residue
cleanup is recorded in
[../migrations/M7-frontend-backend-cleanup.md](../migrations/M7-frontend-backend-cleanup.md).
